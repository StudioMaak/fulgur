# Test harnesses: what each one actually asserts

Seven harnesses guard this repo, and they do **not** all mean the same thing by
"pass". Three compare against a committed oracle, two compare a run against
itself, one compares against a browser-spec expectation file, and one committed
artifact set is asserted by nothing at all.

Knowing which is which decides two things you will get wrong otherwise: whether
a green run is evidence, and whether you may regenerate a file on this machine.

## The map

| Harness | Command | Oracle | Runs on macOS? | Regenerate with |
|---|---|---|---|---|
| Unit | `cargo test -p fulgur --lib` | hand-written assertions | yes | — |
| Integration | `cargo test -p fulgur` | hand-written properties | yes | — |
| GCPM snapshot | `cargo test -p fulgur --test gcpm_snapshot` | 19 byte-exact `.txt` goldens | **yes** | `FULGUR_SNAPSHOT_UPDATE=1` |
| Example determinism | `cargo test -p fulgur-cli --test examples_determinism` | **the run itself** | yes | — |
| Example PDFs | — | **nothing asserts these** | **no — do not** | `mise run update-examples` (Linux/CI) |
| VRT | `cargo test -p fulgur-vrt` | 64 byte-exact PDF goldens | **no** | `FULGUR_VRT_UPDATE=1` (in container) |
| WPT | `cargo test -p fulgur-wpt` | PASS/FAIL expectation files | skips without fetch | `cargo run -p fulgur-wpt --example seed` |

## The three that catch people out

### Example determinism does not compare against `examples/*/index.pdf`

`examples_determinism.rs` renders each example **twice** and asserts the two
renders are byte-identical (`render_example(...out_a)`, `render_example(...out_b)`).
It is the regression harness for the `fulgur-a8s` font-determinism caveat — it
proves the renderer is deterministic, and nothing else.

It never reads the committed `index.pdf`. A behaviour change that alters every
example still passes this test. Do not cite it as evidence that output is
unchanged.

### The committed example PDFs are artifacts, not goldens

The 21 `examples/*/index.pdf` files are asserted by no test. They are
regenerated by `.github/workflows/update-examples.yml`, which runs on every pull
request to `main` and pushes the result back to the branch.

**Do not regenerate them on macOS.** They embed NotoSans, resolved through the
pinned `examples/.fontconfig/fonts.conf` on Ubuntu. `FONTCONFIG_FILE` is a
measured no-op on macOS — fontconfig is not macOS's font mechanism — so the same
command here embeds Helvetica instead, and you would commit an artifact CI
immediately overwrites:

```bash
FONTCONFIG_FILE="$PWD/examples/.fontconfig/fonts.conf" \
  cargo run -p fulgur-cli -- render examples/table-header/index.html -o /tmp/x.pdf
pdffonts /tmp/x.pdf   # => Helvetica on macOS, NotoSans on Linux
```

Because nothing asserts them, a stale example PDF can encode a bug as if it were
intended output and stay that way for months. `examples/table-header/index.pdf`
did exactly that: an example titled "Table Header Repeat" whose header did not
repeat.

### VRT cannot see your change on macOS

`fulgur-vrt` compares PDFs byte-wise against 64 goldens cut on Ubuntu CI. On
macOS, DejaVu resolves to Helvetica and 29 of 64 fail for font reasons alone, so
a real regression hides among them. The goldens reproduce **only** in
`ubuntu:24.04` with `fonts-dejavu-core` 2.37-8 — see the container recipe in
`CLAUDE.md`. Architecture does not matter; the font package revision does.

Never gate on a macOS VRT run, and never regenerate a golden from one.

## The pattern that does work everywhere

`gcpm_snapshot.rs` is the robust shape: it injects Noto Sans through
`AssetBundle::add_font_file` rather than relying on the host's fonts, so its 19
byte-exact goldens pass unmodified on macOS, Linux and Windows. New byte-exact
coverage should follow it rather than VRT wherever the feature under test does
not need a rendered image.

## Coverage scope

CI's coverage job runs `cargo llvm-cov nextest --workspace --exclude fulgur-vrt`.
VRT-only coverage therefore does not reach codecov: a draw path exercised solely
by a VRT reftest reads as uncovered. Put a unit test in the module, or an
end-to-end smoke test in `crates/fulgur/tests/render_smoke.rs`, alongside any VRT
fixture. See the coverage note in `CLAUDE.md`.

## WPT

`fulgur-wpt` runs Web Platform Tests reftests against checked-in expectation
files (`crates/fulgur-wpt/expectations/`), currently 82 PASS / 141 FAIL / 34 SKIP
of 257 for `css-page`. It needs the WPT checkout fetched by
`scripts/wpt/fetch.sh`; without it every phase skips silently, and only the
dedicated CI matrix cell sets `FULGUR_WPT_REQUIRED=1` to turn a skip into a
failure. A green `cargo test -p fulgur-wpt` on a machine that has not fetched WPT
means nothing was run.

Expectation files record current behaviour, not desired behaviour. A `FAIL` line
is a known gap, and flipping one to `PASS` is the deliverable of a fix — see the
`wpt-promote` skill.
